## 三、mod 体系总体评估

### 3.1 两个版本的 mod 生态状态（知识库实证）

| 维度 | 3114（3.11.4） | 415（4.1.5） |
|------|----------------|--------------|
| 生态阶段 | **成熟末期**——官方 3.x 已 EOL，TS 服务端 mod 存量庞大（3114 整合包实测 6 大类迁移过） | **断代重建期**——4.0→4.1 发生 `AbstractModMetadata`→`IModMetadata` 硬断链，**全部 4.0 mod 必然 ReflectionTypeLoadException 拒载**，必须反编译重编译 |
| mod 与服务器耦合 | TS mod 直接调用服务器内部 API（`DatabaseServer.GetTables()`、`ConfigServer.GetConfig()` 等） | C# mod 通过 NuGet `SPTarkov.Server.Core` 编译期绑定 + `[Injectable]` DI 注入 |
| 服务器行为变更的代价 | **极高**——签名/行为改动即破坏存量 TS mod，且 3.x 无官方修复回流通道 | **中等**——mod 依赖编译期契约，服务器 bug 修复若保持 API 签名不变则 mod 无感；但语义修复（如黑名单 `!`）会改变 mod 依赖的行为基线 |
| ModValidator 行为 | 坏 mod 跳过（修复后可 continue） | **任一 mod 校验失败 → 全部 mod 拒载**（`modloader-no_mods_loaded`）——mod 生态对服务器行为的敏感度更高 |

### 3.2 性能需求的正确出口（知识库实证）

`3114-eft016-perf-hotspots.md`（反编译实证）结论：**EFT 0.16 的客户端性能瓶颈集中在 AI 链**（bot 每帧全量串行更新、感知射线风暴、同步主线程寻路、睡眠 bot 感知漏洞）——全部在**客户端**。而 `pilot-experience-performancetweaks.md` 验证了客户端性能 mod 路线：**PerformanceTweaks v0.2.0 灯塔实测平均 FPS +20.2%**。

**推论**：用户感知的"卡顿/掉帧"，服务器端优化只能贡献"响应延迟"部分（任务界面加载、交物品等待），**帧率问题必须走客户端 mod**——服务器端优化在两版本都不是帧率问题的解药。

### 3.3 服务器改动与 mod 体系的相互作用

1. **3114**：服务器是 mod 的行为宿主。我们的改动（签名贯穿 sessionId、缓存行为、概率分布修正）全部落在 mod 的依赖面上——即使单个 mod 无报错，行为组合也可能漂移（第一轮 bot 崩溃的合理怀疑之一）。**在 EOL 的 3.x 上改造服务器 = 与全部存量 mod 为敌。**
2. **415**：4.1 生态正在重建（mod 数量少、作者活跃、上游 SPTarkov 持续迭代）。**修复移植 bug（加 `!`、判空、恢复语义）会让 mod 依赖的行为更接近正确基线**——与生态利益一致；但"性能优化"（改并发模型、删 GC.Collect）会改变 mod 的时序假设，风险同 3114。

## 四、总体裁决：还值得做吗

### 4.1 3114 服务器端：优化不值得，修复已到拐点

**不值得继续的理由：**
1. **收益错位**：性能瓶颈在客户端 AI 链（实证），服务器优化的收益上限是"界面响应快几百毫秒"——已实施的两项（藏身处缓存、任务索引）吃掉了大头
2. **风险已实证**：第一轮全量实施引发 bot 不生成 + 静态容器空；即使二分重做，Step 7-9（会话化 + bot 生成链 + 随机数）仍未验证，是已知的高危区
3. **mod 生态锁死**：3.x EOL，存量 TS mod 锁定服务器行为；任何签名/语义改动都是兼容性炸弹；上游无回流通道，改动永远私有（维护成本全部自担）
4. **人力现实**：单机自用场景下，"经济正确性"（防自己作弊）与"稳定性边际改善"的收益远低于测试成本

**害处（若继续做）：** mod 兼容破坏、回归风险（每步人工冒烟成本高）、私有 fork 维护负担、与上游 3.11 未来的任何修复/合并冲突。
**益处（若继续做）：** 仅剩 Step 3-9 的稳定性/多玩家正确性——对纯单人 localhost 用户几乎不可感知。

### 4.2 415 服务器端：修 bug 值得，性能优化不值得

**值得做的（按 415 报告"最值得修的 10 件事"过滤）：**

| 类别 | 项目 | 理由 |
|------|------|------|
| Critical 一行修复 | TraderAssort `!` / LootGenerator 三连谓词 / RagfairOffer `.Max.Max` / RepeatableQuest break / GiftService / MailSendService 等 15 处移植笔误 | 恢复商店库存、武器箱奖励、任务奖励数量——**玩家可感知的功能恢复**，单行改动、可逐项验证 |
| 崩溃面 | 8 处 `string.Intern` 判空 | 消除 mod 物品包/坏 JSON 导致的整库反序列化失败——**直接关系 mod 生态健康**（4.1 生态重建期，mod 数据质量参差，此修复是 mod 加载容错的核心） |
| 稳定性 | ProfileMigration 循环 try/catch + SaveServer 兜底 | 单坏档拖垮启动的修复——整合包场景（大量 mod + 大量存档）的刚性需求 |
| 死循环 | ItemHelper 两处 + 伴生 NaN | 请求线程挂死防护 |
| 通知链路 | NOTIFY 四件套 | 保险/商人通知通道恢复——每个会话都命中的路径 |
| 安全 | ForwardedHeaders 收紧 + preset Id 校验 | LAN 部署场景真实风险 |

**不值得做的：** 性能类热点（`GC.Collect` 移除、TradeHelper 全局锁改造、O(n²) 排序）——理由与 3114 相同：动并发/时序假设即牵全身，且当前无性能痛点实据（4.1.5 刚发布，无人反馈卡顿）。

**害处（做 bug 修复的风险）：**
- fork 与上游 SPTarkov 的分叉：上游若修同 bug 会冲突（需跟踪上游 commit）
- 语义修复改变 mod 依赖的行为基线（如黑名单 `!` 修复后，依赖"错误行为"的 mod 表现变化）——4.1 生态早期影响小，越晚修影响越大（**修复窗口期论点**）
- 每项修复需回归验证（无自动化测试，人工冒烟）
**益处：** 功能恢复 + mod 生态更稳 + 坏档容错 + 安全闭合，全部落在"玩家与 mod 作者共同受益"的面上。

### 4.3 一句话战略

> 3114：冻结，享受已验证的两项优化。415：趁窗口期修 bug（优先 15 处移植笔误 + 8 处判空 + NOTIFY），性能优化一律不做。

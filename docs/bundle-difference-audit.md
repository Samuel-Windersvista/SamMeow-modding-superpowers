## 二、3.11 -> 4.1 的 bundle 差异（精确列出）

### 差异 1：MonoBehaviour 脚本绑定（理论风险 vs 实测结果）

**理论风险**：4.1 客户端反混淆把 3830 个 GClass、422 个 GStruct、447 个 GInterface 改名。如果 bundle 里的 prefab 引用了旧混淆名，绑定断裂，组件丢失或报错。

**实测结果**：本整合包 **2622 个 bundle 中 0 个引用混淆类名**。bundle 引用的脚本类（PreviewPivot、LoddedSkin、HotObject）在两个游戏中都存在且名称相同。

**结论**：对本整合包无实际影响。但**不保证其他 3.11 整合包**也如此 -- 如果某个 mod 作者在 prefab 上挂了 EFT 内部混淆组件（如 `GClass680` 这类），迁移后会断。这是一个**按 mod 逐一验证**的项，不能一概而论。

### 差异 2：Shader（真正的引擎层风险）

Unity 官方明确：AssetBundle 向后兼容"not guaranteed in all situations"，**shader 是最常见的破坏源**（官方 issue CASE IN-4831、讨论帖 881756 均证实）。

**EFT 0.16.1 (3.11) -> 0.16.9 (4.1) 是 patch 级差异**，shader bundle 可能微调。2019.4 构建的 bundle 里的 shader（尤其 EFT 自定义 shader：Bumped Specular SMap 等）在 2022.3 引擎里依赖向前兼容。

**结论**：低风险但**必须实测**。症状是"紫色模型"（shader 丢失）或材质参数错误。WTT 文档的排障也提到"Purple Model? Reassign textures shaders in Unity"。

### 差异 3：bundles.json 元数据

3.11 的 `IModMetadata` 有 `IsBundleMod` 字段；4.1 删除该字段，改为检测 `bundles.json` 是否存在。**服务端层面**的差异，bundle 文件本身无影响。

### 差异 4：无（引擎序列化格式一致）

两个游戏同引擎（2022.3.43f1），bundle 序列化格式版本一致。之前研究代理声称"3.11 与 4.1 的 bundle 序列化格式版本一致 -> 二进制直接可加载" -- 这部分对。

## 四、迁移验证清单（每 mod 必做）

迁移一个带 bundle 的 mod 到 4.1 时：

1. **复制 bundle 文件** + 更新 bundles.json（删 IsBundleMod 相关逻辑）
2. **实机启动**，检查服务端日志 bundle 加载（CRC32 校验通过、文件存在）
3. **进游戏检查模型**：
   - 模型显示正常？（无紫色模型 = shader OK）
   - 材质/贴图正确？（无纯白/纯黑 = 材质参数 OK）
   - 附件挂点正确？（武器附件位置 = 组件 OK）
   - PreviewPivot 预览图正常？（SDK 脚本绑定 OK）
4. **如有异常**：
   - 紫色模型 -> shader 不兼容，用 Unity 2022.3 + EFT SDK 重建 bundle
   - 组件丢失/报错 -> 脚本绑定断裂，重建 prefab
   - 其他 -> 检查 bundles.json 路径/CRC

## 五、结论

**用户的判断正确：3.11 和 4.1 的 bundle 确实存在差异。** 但差异的实质不是"Unity 版本不同"（两版游戏引擎相同），而是：

1. **85% 的 bundle 是 2019.4 构建的** -- 在 3.11 里靠向前兼容运行，4.1 引擎相同所以兼容机制不变
2. **shader 的 patch 级变化**（0.16.1 -> 0.16.9）-- 低风险但必须实测，症状是紫色模型
3. **MonoBehaviour 脚本绑定** -- 本整合包实测 0 个 bundle 引用混淆类名，无风险；但其他整合包需逐一验证
4. **bundles.json 元数据**（IsBundleMod 删除）-- 服务端 manifest 层面

**迁移策略不变但验证标准要加严**：不能"复制即用"完事，必须做逐 mod 的实机验证（模型显示 + shader + 组件 + 预览图）。

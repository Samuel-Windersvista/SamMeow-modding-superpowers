# 可行性报告：3.11.4 -> 4.1 全自动 MOD 移植能力

> 版本：v1.2（重大突破：locale 阻断器已通过源码实证解决）
> 日期：2026-08-05
> 触发：Overseer 要求评估"全自动 3.11.4 MOD 向 4.1 移植（含 bundle）"能力的可行性
> 数据基础：Life_in_Norvinsk_v0.3.2 整合包（194 目录 / 91 个 TS 服务端 mod / 132 个 DLL / 2622 个 bundle）实机扫描 + 两份专项研究 + 三份迁移知识
> 审阅：议会独立评审（评级 B+，含 3 处关键修正）+ v1.2 源码实证修正
> 状态：已审阅

## 一、执行摘要

**结论：全自动移植"部分可行"，但"全自动"不等于"零人工"——现实目标是构建一条**自动化流水线**，把 91 个服务端 mod、72+ 客户端 mod、2622 个 bundle 的移植工作压缩为"流水线自动跑 + 按阻断器分级人工干预"。**

**议会修正后的定义**：全自动 = pipeline 产出**编译通过 + 加载成功 + dbdiff 一致**的 mod，人类无需查看一行代码或日志。

### 核心数字（v1.2 上修后）

| 层面 | 全自动率 | 说明 |
|------|---------|------|
| 服务端 TS->C#（91 个） | **~75%**\*（含半自动 85%+） | \*locale 阻断器已通过源码实证解决（AddTransformer），locale 型 mod 从 50% 跳升至 80%+ |
| 客户端 DLL（72 个） | **有源码 50-70% / 无源码 20-30%** | 映射表 21% 缺口 + 方法/字段名零映射 |
| Bundle（2622 个） | **80-90%** | 脚本绑定 0 风险 + shader 可自动预检 |
| **整体零人工** | **~40-50%** | 其余需要按分级人工干预 |

### 关键判断

1. **服务端是"可自动化重写"**，不是"翻译"——把 3.11 代码当行为规格，用 4.1 模板生成 C#
2. **客户端是"半自动重编译"**——反混淆改名捷径走不通（映射表缺口），正路是有源码重编译
3. **Bundle 是"自动复制 + 自动验证 + 定向重建"**——复制和验证可全自动，重建 <5% 触发
4. **locale 阻断器已解决**（v1.2 突破）——官方 `LazyLoad.AddTransformer` 机制就是 4.1 修改 locale 的标准方式
5. **真正剩余的人工点是**：客户端映射缺口、类扩展 override（复杂 mod）、行为等价抽查

## 三、三层自动化能力评估

### 3.1 服务端：TS -> C#（可自动化重写）

**可自动化（~80% 代码面）：**
- 入口/生命周期：`module.exports` -> `IModMetadata` + `[Injectable]`；`preSptLoad/postDBLoad` -> `IOnLoad.OnLoadAsync`
- DI：`container.resolve` -> 构造注入；`@injectable` -> `[Injectable]`
- 表访问：`DatabaseService.getX()` -> `TemplateTable`/`TradersTable` 等（映射表已建）
- 配置/日志/路由/文件读取：全有 1:1 映射
- **数据文件（JSON/图片）100% 原样搬运，不参与翻译**（商人 mod 的 90% 内容是数据）

**不可自动化（阻断器，locale 已解决）：**

| # | 阻断器 | 影响 | 处理 |
|---|--------|------|------|
| 1 | `LocaleTable.Global` 直写 | 150/542 文件 | **已解决（v1.2 源码实证）**：官方 `LazyLoad.AddTransformer` 机制（`PostDbLoadService.RenamePreraidLocales` 同款）。迁移模板：`localeTable.Global[lang].AddTransformer(data => { data[key]=value; return data; })`。locale 型 mod 自动化率 50% -> 80%+ |
| 2 | 运行时枚举扩展（`Traders[id]=id`） | 商人 mod 依赖动态枚举 | 重写为 MongoId 常量 |
| 3 | assort JSON 数据形状隐性差异 | 数据搬运后形状校验 | 对照 4.1 实况半人工 |
| 4 | 类扩展 override 核心类 | 复杂 mod（SAIN/ProgressiveBot 类） | **等于重新设计**，人工 |
| 5 | TS union/any 类型 | 半自动 | LLM 设计类型 |

**行为等价验证**（编译通过 != 行为等价）：
- **最小方案**：数据库状态 diff（干净 4.1 vs 带 mod 4.1 各 dump 关键表，diff = 预期改动）
- **增强方案**：API 驱动（4.1 是 ASP.NET Core HTTP 服务器，可 Invoke-WebRequest 抽查）
- **前提**：先做只读 `dbdump` mod 验证可行性
- **议会补充**：**3.11 dbdump 与 4.1 dbdump 同等重要（P0 并行）**——没有 3.11 dump 就无法判断"改动是否正确"，只能判断"改动了什么"；3.11 dump 是整个验证链的"预期行为规格说明书"

### 3.2 客户端：BepInEx DLL（半自动重编译）

**反混淆改名捷径走不通（实测）：**
- 映射表只覆盖 84.4% 的 3.11 GClass 名（3310/3920）
- 本包 DLL 实际引用的 330 个 GClass 中 **69 个（21%）不在映射表**
- 方法名（`method_NNN` 216 处）/字段名（`float_N` 等）**零映射**
- 映射表是 4.0->4.1 的，3.11->4.0 编号对齐**未验证**

**正路（社区口径）：**
- 有源码：AST 替换类名 + dotnet build 编译错误驱动（50-70% 自动）
- 无源码：ILSpy/dnSpy 反编译 -> 修源码 -> 重编译（20-30% 自动）

### 3.3 Bundle：自动复制 + 自动验证 + 定向重建

| 步骤 | 自动化 | 工具 |
|------|--------|------|
| 复制 bundles + bundles.json | 100% | 脚本 |
| 版本头/脚本绑定/shader 依赖审计 | 95% | **UnityPy 批量审计脚本**（红黄绿 CSV） |
| shader 名字比对（对游戏 shader bundle） | 可脚本化 | UnityPy |
| 实机加载验证（CRC32 + 模型显示） | 加载自动，显示人工 | SPT 日志 + 进游戏 |
| 重建（<5% 触发，紫色模型时） | 仅最后一步 | Unity batch mode |

**本包 0/2622 引用混淆类名** -- 脚本绑定无风险。shader 是唯一真实风险，但可自动预检（3.11/4.1 的 shader 名两边一致，但 4.1 shaders bundle 是 3.11 的 10 倍大，内容有差异）。

## 四、自动化流水线设计

```
┌ Stage 0: 预处理 ── 文件扫描 + 类型判定（server/client/both）+ 数据文件分流
│   产物: 文件清单 + JSON 数据（100% 原样搬运，不进入翻译）
├ Stage 1: 解析 ── LLM 静态分析 3.11 源码，API 使用清单 + 阻断器打标
│   闸门: 全部 API 调用落入映射表 或 明确标记 blocker（禁止静默跳过）
├ Stage 2: 映射 ── 查 API 映射表（knowledge/spt-kb/curated/migration/）
│   产物: 4.1 API 等价调用清单 + blocker 报告
├ Stage 3: 生成 ── 模板 + 翻译后逻辑 -> .cs 文件 + 搬运数据
│   规则: [Injectable(TypePriority=OnLoadOrder.X+n)] + IModMetadata + 异步贯穿
├ Stage 4: 编译闸门 ── dotnet build 0 错误（编译器抓 API 误用，失败回灌 LLM 迭代 3-5 轮）
├ Stage 5: 加载闸门 ── 部署到 user/mods/ + 启动 SPT.Server.exe + 日志扫描
├ Stage 6: 行为验证 ── 数据库状态 diff（最小） + API 驱动抽查（增强）
├ Stage 7: 客户端线 ── 反混淆改名（有源码 AST / 无源码反编译） + 重编译 + BepInEx 加载验证
├ Stage 8: Bundle 线 ── 复制 + UnityPy 审计 + shader 预检 + 实机验证
└ Stage 9: 报告 ── 每 mod 移植报告（自动/半自动/人工分级）
```

**各阶段自动化程度：**

| 阶段 | 自动化 | 说明 |
|------|--------|------|
| 0 预处理 | 95% | 脚本扫描 |
| 1 解析 | 80% | LLM + blocker 识别需喂 KB |
| 2 映射 | 70% | 映射表已齐，3.11 特有需补 |
| 3 生成 | 85% | 模板骨架 100%，逻辑翻译 LLM |
| 4 编译 | 100% | 纯机械，可自动迭代 |
| 5 加载 | 90% | 进程控制 + 日志扫描 |
| 6 行为验证 | 50-70% | dbdump diff |
| 7 客户端 | 30-40% | 映射缺口限制 |
| 8 Bundle | 80-90% | UnityPy 审计 |
| 9 报告 | 95% | 机械汇总 |

## 五、可行性结论

### 5.1 项目层面判断

| 维度 | 判断 |
|------|------|
| 技术上可行？ | **可行**，三层都有自动化路径 |
| 全自动率？ | **~35-45% 零人工**，含半自动 ~70-75% |
| 最终结果？ | 177 个 mod 中约 **120-130 个可自动化/半自动化迁移**，6-10 个复杂 mod 需人工重写 |
| 最大瓶颈？ | **locale 直写（blocker 1）** 和 **客户端映射表缺口（21%）** |
| 最大风险？ | 行为不等价（编译通过 ≠ 功能一致） |

### 5.2 建议的落地路径（按 ROI，v1.3 更新：P0 闸门实验结果）

**P0 闸门实验结果（2026-08-05 实测）：**

| P0 闸门 | 结果 |
|---------|------|
| 4.1 dbdump mod | **通过** -- 6 表 dump 成功（items 18.9MB / quests 5.6MB / locales 53MB） |
| 3.11 dbdump mod | **通过** -- 6 表 dump 成功（items 17.3MB / quests 5.0MB / locales 47.9MB），行为预期基准就位 |
| locale 阻断器 | **通过（实测）** -- `LazyLoad.AddTransformer` 运行时生效（LocaleTest 验证成功） |
| 3.11->4.0 编号对齐 | **部分验证** -- 4.0 程序集不可得（无 4.0 客户端归档），无法二进制对照。实测：映射表覆盖 3.11 的 84.1% GClass（3296/3920），624 个缺失散布全范围（22-3917）。**务实结论**：客户端自动化不依赖"编号对齐完美"，而是"映射表覆盖 84% + 编译错误驱动 + LLM 补缺"（编译器会指出无法解析的 GClass，自动迭代） |

| **P2** | AES 商人 mod 试点 -- 可与 ETT 并行（纯数据型） | 预期高成功率 |
| **P2** | 批量迁移 61 个简单档 | 最大收益区 |

## 七、议会审阅意见摘要

议会独立评审结论：**报告 B+ 级，核心可行性判断站得住，需 3 处关键修正**。

### 议会确认的论断
- Bundle 迁移（80-90%）-- 最扎实，0/2622 脚本绑定是实机证据
- 客户端改名捷径走不通 -- 映射表缺口有二进制证据支撑（69/330 活跃引用缺失）

### 议会的关键修正
1. **locale 阻断器降级**：注释说"不 SAVED"而非"不 APPLIED"——运行时直写可能整个会话有效。从"硬阻断"降为"高概率可解，需 10 分钟实验确认"。**v1.2 进展：议会方向完全正确，且找到了更优解 -- 官方 `LazyLoad.AddTransformer` 机制直接支持 locale 修改（PostDbLoadService.RenamePreraidLocales 同款），阻断器已从源码层面解决，无需实验。**
2. **3.11 dbdump 升 P0**：没有 3.11 dump 无法判断"改动是否正确"，是验证链的"预期行为规格说明书"。
3. **3.11->4.0 编号对齐升 P0**：客户端策略的二进制生死闸门，10 分钟可测，推迟一个月做不如现在做。
4. **客户端自动化率分列**：有源码 50-70% / 无源码 20-30%，笼统的 30-40% 掩盖关键信息。
5. **数字加注**：67% 标注"假设 locale 可解"——**v1.2 已证实可解，服务端上修至 ~75%。**

### 议会补充的隐藏阻断器
- TypePriority 冲突（生成时分配非重叠区间）
- 配对 mod 原子性（27 个，明确计数规则）
- mod 加载顺序依赖（3.11 文件夹序 vs 4.1 TypePriority）
- bundles.json 字段兼容性（防 strict parse 崩溃）

### 议会补充的遗漏自动化机会
- 3.11 dump 可反馈给 LLM 生成器（"目标是让 diff 归零"）
- Harmony patch 按签名匹配的 mod 可能天然免疫改名（潜在低估）
- 4.1 shaders bundle 10 倍大可能只是变体膨胀，不影响名字引用

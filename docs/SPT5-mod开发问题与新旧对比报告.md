# SPT 5.0 mod 开发：遇到的问题、难点与新旧对比（人话版）

> 日期：2026-10-05
> 性质：阶段性总结（截至 2026 年 9 月底的实际开发记录）。
> 对象：从零开发的 SPT5 客户端插件（tarkov-runtime-bridge 局内桥）、服务端 mod（tarkov-active-probe 活跃探针）、以及多个 4.x → 5.0 移植项目（AccurateCircularRadar 雷达、NoStaminaDrain 体力等）。
> 说明：本文刻意少用行话；确实需要的术语，附录 A 有"大白话"对照表。

---

## 0. 一分钟版本

1. **5.0 的客户端是一次换地基。** 游戏本体从 Mono 运行时换成了 IL2CPP，插件框架从 BepInEx 5 换成 BepInEx 6，mod 的编译目标从 .NET Framework 换成 .NET 6。旧版客户端 mod 的每一处代码都要重新检查过才敢说能跑。
2. **难的不是"找不到东西"，而是"看着一样、其实不一样"。** 类名和接口名基本都保留了，编译也很容易通过；真正的坑在运行时——不报错、不崩溃，功能悄悄失效（静默失败）。
3. **崩起来不给调试机会。** IL2CPP 的严重错误常常直接让游戏进程退出，普通 try/catch 拦不住；只能靠日志和外部工具取证。
4. **服务端反而是避风港。** 4.1 → 5.0 服务端框架几乎没变，改版本号重编译即可；服务端真正的历史大断层在更早的 3.11 → 4.x（从 TypeScript 换成 C#），与 5.0 无关。
5. **到目前为止，踩过的坑已经变成方法。** "先扫描再挂钩、不相信没报错、每一步留证据"——这些已写进移植技能和知识库，下一次移植会明显更快。

## 1. 背景：5.0 换掉的到底是什么

### 1.1 三代版本一览

| | 3.11 时代 | 4.x 时代 | 5.0 时代 |
|---|---|---|---|
| 服务端 | TypeScript | C# | C#（与 4.x 基本一致） |
| 客户端运行时 | Mono | Mono | **IL2CPP** |
| 插件框架 | BepInEx 5 | BepInEx 5 | **BepInEx 6** |
| 客户端 mod 编译目标 | netstandard2.1 | net48 / netstandard2.1 | **.NET 6** |
| 游戏本体 | EFT 0.16 之前 | EFT 0.16.x | **EFT 1.1.5** |

### 1.2 白话解释：IL2CPP 改变了什么

- 以前（Mono）：游戏代码像**一本翻开的 C# 书**——类、方法、方法体都能直接读到。
- 现在（IL2CPP）：游戏代码被提前翻译成 C++ 再编译成原生机器码；留给 .NET 侧的只是一屋子**"传话员"**（interop 代理）。名字和对外接口都在，但方法体是空的——它们只负责把呼叫转达给原生代码。
- 结果：**名字都不是问题，转达的过程才是问题。** 转达可能被拒绝、被误解、在半路静默出错，甚至直接让进程崩溃。

### 1.3 走到今天的时间线（简）

| 时间 | 里程碑 |
|---|---|
| 09-13 | 首个自定义 SPT5 服务端 mod 经 MO2 加载成功（从"能进游戏"到"能改游戏"） |
| 09-14 ~ 09-15 | 从零开发 SPT5 客户端桥插件（BepInEx 6 + IL2CPP）；三项关键假设实机验证成立；三局真实 raid 验收通过 |
| 09-16 | 第一个完整的 4.x → 5.0 移植项目（雷达）：实机六轮修复闭环，全功能通过 |
| 09-27 | SPT5 mod 模板三件套（客户端 / 服务端 / 配对）完成 |
| 09-28 | 最深的一个坑（补丁"封送"损坏游戏数据）完成复盘并归档进知识库 |

## 2. 实际遇到的主要问题与难点

### 2.1 编译能过、运行翻车——"传话员"不会告诉你它没听懂

这是 5.0 最高频的一类问题，共同点：**编译全绿，进游戏就出鬼**。

- **判断类型失效**：`is`、强制转换、`GetType()` 对代理对象统统不可靠（编译通过、运行时永远判否）。统一改用 `TryCast<T>()` 才能正确判断。
- **功能被"拆掉了"**：有些 API 在打包时被删（如创建系统字体的方法、导航网格三角化等），类型还在、编译能过，一调用就抛异常——因为打包时"觉得没人用"。
- **默认值是陷阱**：给可选参数传语言默认的"空值"，在进入原生代码前就会炸（报空引用）；必须显式构造一个"真的空"传进去。
- **私有字段找不到了**：反射按老办法找字段会扑空——它们在这层被换成了"属性"形态。
- 共同结论：**"能编译"只说明名字对；"能调用"必须在游戏里实测。**

### 2.2 补丁不再"打上就灵"——挂钩的三重陷阱

以前给游戏方法"前后插代码"（打补丁）是家常便饭；在 IL2CPP 下它变成了高风险操作，实测有三类陷阱：

1. **打了补丁反而弄坏原版数据。** 某些方法参数里带着"特殊结构的数据"，补丁工具在传递时会拆开重装，而它对这个数据形状的假设不成立，字段会错位。最反直觉的是：**哪怕你的补丁只看一眼、原样放行，也会把游戏数据弄乱**——不崩溃、不报错，只是行为悄悄变怪。这是到目前为止最隐蔽的一个坑（例：某 bot 项目里，bot 的决策数据被整片清空，表面却一切正常，靠开关对比才定位到）。
2. **有些补丁一打就崩。** 携带特殊结构参数的补丁可能编译、审查全过，实机一操作直接进程级崩溃（例：雷达 mod 一次拖拽即崩）。所以移植前的"补丁目标签名扫描"是必经步骤。
3. **"打上了"不等于"生效了"。** 三种原因会让补丁变成空炮：
   - 小方法被编译器"揉"进了调用处（内联），原入口早就没人走；
   - 目标方法根本不在实际执行路径上（游戏走的是另一条路）；
   - 上游版本里那个方法名已经不存在了（改名或换了形态）。
   对策：挂钩前先扫描"这个方法到底有没有人调用"，并用"游戏自己怎么做"作为权威参照。

### 2.3 崩溃不给调试机会

- IL2CPP 的崩溃常是**进程级**的：内存访问出错，整个游戏直接退出，try/catch 完全拦不住。典型案例是调用某个"虚属性"时直接触发崩溃——修复办法是绕开它，改用同类非虚的替代入口。
- 崩溃时的取证三件套：BepInEx 的错误日志（ErrorLog）、游戏自身日志（Player.log）、Windows 事件日志；此外自建的桥插件还能读局内实时状态，配合定位。
- 教训：日志文件每次启动都会覆盖——出过事就先快照，再重启。

### 2.4 mod 自己闯的祸：异常、资源与连锁故障

- **补丁里的异常会穿透到游戏代码**，直接闪退。所有补丁体必须自己接住异常，绝不向外抛。
- **一个订阅抛异常，会连带跳过同一段里后面的订阅**：桥插件曾因此整类"伤害/死亡事件"消失（异常被吞掉，后面的订阅没执行）。
- **删对象删错目标**：移植时沿用了上游的"销毁整个游戏对象"写法，结果把游戏世界对象一起删了，连锁崩坏；正确做法是只销毁组件自己。
- **资源没人"抓住"就会丢**：打包资源不放在静态引用上，场景切换后就失效；失败路径要把引用留住。
- **一个数据源出错会"毒化"整条链**：估价功能里一个价格来源抛异常，被外层统一接住后把整锅结果丢弃（连已经算对的部分也扔了）；修复是每个来源独立隔离、出错熔断，其余照常工作。
- 一句话教训：**"没崩"不等于"没问题"，静默失败比崩溃更危险。**

### 2.5 装进游戏也不轻松：MO2 虚拟文件系统

- mod 新建的配置文件会被 MO2 重定向到 `overwrite/` 目录——在游戏目录里怎么找都找不到，验证要去那里找。
- 游戏运行时 DLL 被锁定，部署/替换前必须先退出游戏。
- 正确姿势：以"覆盖层"形式交付（mod 根目录对应游戏根目录，运行时由 MO2 投影进游戏）——客户端、服务端都已实测走通。
- 部署卫生很重要：出现过"文档写着已部署、实际没部署"的偏差；现在要求部署后哈希核对、留备份、记台账。

### 2.6 配置界面（F12）的碎玻璃

- **下拉框会刷屏报错**：枚举选项默认渲染成下拉框，而下拉框依赖一个已被"拆掉"的界面方法，于是每帧都尝试装载失败——单次会话刷出 6400 条以上错误日志，界面失衡。解决办法：改纯文本输入，或自己画一组按钮。
- BepInEx 6 把"快捷键"类型拆成了独立组件，不引用就无法读取按键配置；颜色类型的配置转换器也缺省没有，都要额外补。
- **换语言会换出"孤儿配置"**：配置条目的名字如果跟着语言走，切一次语言就会生成一套新键名，旧键变成看不见的孤儿（表现为"菜单突然变英文"）。需要专门的键名迁移逻辑。
- 这些问题全部修完并实机验证后，F12 界面才算真正可用（雷达 mod 已通过）。

### 2.7 缺数据怎么办：客户端拿不到，就让服务端下发

IL2CPP 化之后，很多数据在客户端"拿不到就是拿不到"：

- 物品的参考价字段恒为 0；战利品容器没有"是否被搜过"的标记；任务区域数据只在服务端。
- 成熟模式：**服务端读数据文件 → 精简后走自定义路由下发 → 客户端拉取并缓存**；服务端缺失时客户端自动降级，不硬崩。
- 两个高频细节：查表必须用"模板 ID"而不是实例 ID（用错就全军覆没，曾经整项功能查不到一个物品）；SPT 的 PMC 敌人被标成"Scav 阵营"，按阵营分类会全部误判——必须"先看角色、再看阵营"。

### 2.8 服务端：反而没有大变化

- 4.1 → 5.0 服务端框架没有破坏性变更：接口、依赖注入、路由、加载顺序都照旧；移植 = 改版本号区间 + 重编译。
- 少量擦伤：个别请求模型被删/换了形态、部分字段有扩充——都是小修。
- 5.0 新增的赛季、通行证等系统是**可选扩展点**：旧 mod 不用它也不会坏。
- 但要小心：**4.1 时代的服务端知识对 3.11 早就作废**（那个时代的 package.json、配置服务、数据库服务等机制早已不存在）——服务端真正的学习断层发生在更早的 3.11 → 4.x，不是 5.0。
- 服务端自身也踩过小坑：日志要"按字节增量"读取（半行等待、文件被截断时重来）、响应有统一信封格式、拿当前玩家 ID 的路径要摸清——都已实测解决。

### 2.9 干活工具的升级：逆向链路

- 读游戏逻辑的手法换代了：Il2CppDumper 导出元数据、Cpp2IL 输出近似汇编片段（ISIL）、Ghidra 反编译原生函数。
- 一个重要的好消息：**"类名变代号"是误解**——1.1.5 的类名是完整保留的（16,435 个类型，代号类数量为 0），约 95% 与 4.1 同名。障碍不在名字，在方法体。
- 大部分补丁**不需要**读方法体，按签名挂钩即可；只有"要精确复刻逻辑、找真正的数据改动点"时才要读汇编。
  - 为例：体力锁定 v1 只给"看起来像"的扣减方法打了补丁——日志显示补丁确实触发了，体力却照掉；读汇编才发现真正逐帧扣体力的是另一个函数。**"看名字选目标"会选错，读代码才能找到真凶。**
- 成本也要心里有数：对 118MB 的二进制做反编译，实测约 4 小时 20 分（内存要 8GB）——按需使用，别当日常工具。

## 3. 与 SPT4 等旧版本相比，差别在哪

### 3.1 客户端：一次真正的"换代"

| 方面 | 旧版（3.11 / 4.x） | 5.0 | 对开发者的实际意义 |
|---|---|---|---|
| 运行时 | Mono | IL2CPP | 方法体不可读；代理"传话"；崩溃不可拦截 |
| 插件框架 | BepInEx 5 | BepInEx 6 | 插件基类、入口点、生命周期全换 |
| 编译目标 | net48 / netstandard2.1 | .NET 6 | 工程文件基本重写 |
| 游戏程序集 | `Managed/Assembly-CSharp.dll`（真逻辑） | `BepInEx/interop`（空壳） | 找类容易、看逻辑难 |
| 补丁库 | Harmony 2 / `SPT.*` | HarmonyX / `SPTushonka.*` | 多数代码只改引用；但行为细节有大量新坑 |
| 游戏本体 | EFT 0.16.x | EFT 1.1.5 | 类名、字段大量微调（约 21 条确认改名；一类请求参数被整体重构为泛型形态） |

一句话总结：**旧版经验不是作废，而是"半可用"——思路还能用，每一条都要重新验证。**

### 3.2 服务端：断层在更早的地方

- **3.11 → 4.x**：几乎是重写（TypeScript → C#；`package.json` 元数据 → DLL 内声明；配置/数据库服务 → 依赖注入）。这才是服务端真正的断层。
- **4.1 → 5.0**：几乎无痛（接口、加载顺序照旧；只有少量请求模型增删和字段扩展）。
- 所以"SPT5 服务端 mod 难做"是个误解；真正需要心理准备的是 3.11 时代的人第一次进入 4.x/5.x 世界。

### 3.3 两段断层，性质完全不同

| 迁移 | 断层位置 | 性质 | 工作量感受 |
|---|---|---|---|
| 3.11 → 4.x（服务端） | 服务端 | 换语言、换架构 | 近乎重写 |
| 3.11 → 4.x（客户端） | 客户端 | 类名去混淆 | 改名 + 重编译（有映射表） |
| **4.1 → 5.0（客户端）** | **客户端** | **换运行时** | **系统性重验，逐个补丁点修复** |
| 4.1 → 5.0（服务端） | 无 | 版本区间 + 重编译 | 低成本 |

### 3.4 最容易误解的几件事

1. **"5.0 服务端要重写"** —— 错。要重写的是 3.11 → 4.x 那一步；5.0 服务端很省心。
2. **"IL2CPP 把类名混淆成代号了"** —— 错。名字完整保留，困难在方法体不可见。
3. **"看不到逻辑就没法改 mod"** —— 错。按签名挂钩不需要读方法体；只有精确复刻才需要读汇编。
4. **"补丁打上了就会生效"** —— 错。可能因内联、路径、改名而静默失效；"应用成功"不等于"真的命中"。
5. **"旧 mod 换个引用、重编译一遍就能跑"** —— 错。几乎每个补丁点都要重新核验，还有一整类新的运行时陷阱。
6. **"5.0 不能用于生产"** —— 已过时。5.0 已正式发布并进入维护（由社区 fork 承接），不再只是预览品。

## 4. 到目前为止沉淀出的"硬规矩"

1. **先扫描、后挂钩**：补丁目标先做签名扫描、调用点扫描，确认"能挂、有被执行"再动手。
2. **不相信"没报错"**：没崩、没报错都不算证据；用"开/关对比"和数据分布来验证。
3. **每个危险点都准备替代路径**：换成安全的挂载入口、换用非虚成员、把数据改由服务端下发。
4. **补丁体一律自己接住异常**；多个订阅各自独立保护；补丁逐类应用，互不牵连。
5. **崩溃取证靠日志组合拳**：错误日志 + 游戏日志 + 系统事件日志 + 局内探针；先快照再重启。
6. **部署讲卫生**：退游戏再部署、哈希核对、留备份、记台账。
7. **数据链每个来源独立隔离**，一个失败就熔断，绝不拖垮整条链。
8. **拿不到的数据走服务端**；查表前先确认真值（模板 ID、角色字段这类细节）。
9. **大规模迁移前先做小实验**（spike）：在游戏里验证关键行为，再全面动工。
10. **教训写回知识库**：本轮所有坑均已归档为可复用的经验条目（见附录 B），同类问题不再从零查起。

## 附录 A：术语速查（大白话）

| 术语 | 一句话解释 |
|---|---|
| Mono | 旧版运行时；游戏逻辑以可读的 C# 形式存在 |
| IL2CPP | 游戏脚本先转成 C++、再编译成本地代码的打包方式；托管侧只剩接口壳 |
| interop / 代理 | 托管世界调用原生代码的"传话员"层 |
| BepInEx | 给 Unity 游戏挂插件的框架（5 是旧版、6 是新版） |
| Harmony / 补丁 | 不改游戏源文件，往游戏方法前后插入自己代码的技术 |
| detour（挂钩） | 让游戏执行到某方法时改走你的代码 |
| 封送 | 托管世界与原生代码之间传递参数时的"打包/拆包"过程 |
| 剥离 | 打包时删掉"看起来没人用"的方法；运行时才发现没了 |
| AccessViolation（AV） | 内存访问越界的严重崩溃；进程级，拦不住 |
| 内联 | 编译器把小函数"揉"进调用处；原入口没人走，挂钩必然失效 |
| MO2 / usvfs | 模组管理器及其虚拟文件系统；运行时把 mod 文件"投影"成游戏文件 |
| 覆盖层 | 改动以独立 mod 目录形式保存，不直接写游戏安装目录 |
| interop 程序集 | BepInEx 从 IL2CPP 游戏导出的"接口名单"程序集；只有名单，没有实现 |
| ISIL / Ghidra | 读原生代码的工具链：前者输出近似汇编片段，后者做反编译 |
